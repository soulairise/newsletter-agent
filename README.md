## 다섯 단계

```
① 수집  →  ② 선별  →  ③ 취재  →  ④ 검수  →  ⑤ 발행
 RSS       예선→본선   본문+요약   원문 대조   Discord
```

| 단계 | 하는 일 | 고른 방식 |
|---|---|---|
| ① 수집 | RSS 8곳에서 24시간 창 안의 글을 모으고 중복 제거 | **RSS·Atom** (사다리 2칸 — 인증 불필요) |
| ② 선별 | 후보를 묶음으로 나눠 예선 → 살아남은 것만 본선 | **2단 상대평가** |
| ③ 취재 | 원문 본문을 뽑아 헤드라인·요약·why 세 칸으로 | **검증 방법이 다르면 칸을 나눈다** |
| ④ 검수 | 요약이 원문을 벗어났는지 대조 | **LLM 대조** (문자열 대조는 번역·환산을 오탐) |
| ⑤ 발행 | embed 카드로 디스코드에 전송 | **웹훅** |

LLM 호출은 하루 12번 남짓입니다. 후보를 전부 독립 채점했다면 후보 수만큼 필요했을 것입니다.

## 소스

`measure_sources.py` 로 세 관문을 재서 고릅니다 — **G1 본문**(요약할 재료가 나오는가),
**G2 생존**(최근에도 글이 올라오는가), **G3 접근**(robots.txt 가 허용하는가).

tier 1(당사자 발표)은 선별 경쟁에서 면제하되 상한(3건)을 두고, 검사는 그대로 받습니다.

```sh
uv run python measure_sources.py    # 소스를 재고 채택 목록을 출력
```

## 실행

```sh
./run.sh          # dry-run — 보내지 않고 무엇을 보낼지만 출력
./run.sh --send   # 실제 발행
```

키는 환경변수로만 전달합니다. 소스 코드에는 들어 있지 않습니다.

| 변수 | 쓰는 곳 |
|---|---|
| `OPENAI_API_KEY` | ② 선별 · ③ 취재 · ④ 검수 |
| `DISCORD_WEBHOOK_URL` | ⑤ 발행 |
| `DRY_RUN` | `0` 이어야 실제로 보냅니다 (기본 `1`) |
| `NEWSLETTER_BRAND` | 디스코드에 뜨는 발행자 이름 |

로컬에서는 `run.sh` 가 `~/.config/harness-lab/env` 와 `~/.config/newsletter-agent/env` 를 읽습니다.
자동 실행에서는 GitHub Secrets 에서 주입됩니다.

## 자동 실행

`.github/workflows/daily.yml` — 매일 **07:00 KST**(= 22:00 UTC).
깃허브 Actions 화면의 **Run workflow** 버튼으로 즉시 실행도 됩니다.

> cron 은 UTC 이고, 예약 실행은 보통 5~15분 늦습니다.
> 저장소에 60일간 커밋이 없으면 예약이 자동으로 꺼집니다.

## 설계에서 배운 것

- **프롬프트는 요청이지 보장이 아니다.** 스키마 설명에 "다섯 중 하나"라고 적어도 안 지켜져서,
  `Literal` 로 코드에서 강제했습니다. 매체 상한과 같은 사건 중복 제거도 코드로 셉니다.
- **조용한 실패를 막는다.** 소스 하나가 죽어도 나머지는 모으되, 죽은 곳을 로그에 남깁니다.
  기록이 없으면 건수가 줄었다는 것 말고 아무 단서가 없습니다.
- **검수가 0건 불합격인 날은 좋은 소식이 아니라 확인이 필요하다는 신호다.**
  검사 장치는 고장 나도 티가 나지 않습니다.

`store/metrics.jsonl` 에 실행마다 깔때기 숫자를 남깁니다.
